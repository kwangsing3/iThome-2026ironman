# 受眾分析(四面向)

依專案定義的受眾,對每篇已成稿/骨架文章提出「各受眾想看什麼 + 改善建議」。

## 四個受眾(評估軸)

- **A** iThome 讀者/評審 — craft、類別契合(生成式 AI)、GEO/SEO、真實上線護城河、可複製硬貨
- **B** 公司同事/抗拒 AI 的一線同事 — 不被威脅、認得系統、留白邀請(不下指導棋)、參與空間
- **C** 組織/決策層、部門主管 — ROI/成本帳、責任邊界與失誤控制、政治風險、沒職權怎麼推
- **D** 潛在雇主/客戶 — 收斂成系統的能力、判斷力痕跡、真實使用證據、專業不浮誇

---

## 怎麼重新生成這份分析(報告生成提示詞)

> 這份分析刻意**不長期保存**(文章會一直改,舊分析很快過期)。要重跑時,照下面的配方即可重新產出「逐篇分析(每篇一檔)＋系列總體報告」。
> 設計原則:**每篇文章用一個獨立子代理讀**(context 隔離,避免一次載入 20+ 篇撐爆脈絡、也避免跨篇污染);主代理只做最後彙整。

### 步驟

1. **盤點要分析哪些篇**:掃 `article/*.md`,已成稿或有骨架的都算(目前約 D01–D09、D14–D29;D10–D13、D30 尚未建檔就跳過)。
2. **每篇派一個子代理**,把下方〈子代理提示詞〉貼給它,`{DXX}` 換成該篇編號。**多篇可平行**。
   - **model 建議用 Opus**:這是編輯級深度判讀(抓跨受眾張力、分辨「生成式判讀 vs 自動化」、聞出保密累積風險),小模型會**取巧套格式**——格子填滿了、卻多是泛泛評語而非扣著具體句子的觀察。品質重於成本時別省這個。真的要省再退 Sonnet,但預期分析會變淺。
3. **每個子代理輸出一份逐篇分析**,主代理各存成 `受眾分析/DXX.md`。
4. **全部回收後,主代理**照下方〈系列總體報告提示詞〉,彙整成 `受眾分析/系列總體報告.md`,並回頭把本 README 的逐篇索引表補上。

### 子代理提示詞(每篇一個,`{DXX}` 換成篇號)

```
你是 iThome 鐵人賽 30 天連載的校閱子代理。系列主張:「AI 負責人類到不了的地方
(規模/速度/不間斷),而不是取代人」。作者是某系統整合商的工程師(公司一律不具名)。
三根實作支柱:向原廠下單系統(CCW)/ 每日 CVE 通報 / 設備運作分析。

任務:只讀 article/{DXX}.md 這一篇,站在下面四個受眾角度,分別回答「這個受眾會想在
這篇看到什麼」「這篇現在給到了沒、該怎麼改善」。只分析這一篇,不要臆測其他篇。

四個受眾(逐一都要做):
A. iThome 讀者/評審 — 類別契合(這是「生成式 AI」組,LLM 到底做了什麼判斷/生成,而非
   被讀成純自動化)、結論先行/問句 H2/可獨立抽取(GEO)、真數據/截圖/可運行程式碼這種
   硬貨、真實上線的第一手經驗(E-E-A-T)、可複製或至少看懂做法。
B. 公司同事/抗拒 AI 的一線同事 — 被接手的是「規模/速度/不間斷」那片人守不住的疆域、
   不是「我這個人」;認得出系統長什麼樣;「人被釋放去哪」是開放邀請、留白,不被下指導棋
   指定「你該去做判斷/責任」;有參與、自願、看得到好處的空間。
C. 組織/決策層、部門主管 — 導入 ROI、token 成本 vs 人力節省的真實帳;責任邊界與失誤控制
   (輔助/半自動/全自動的權責);政治風險(不打掉重練、不讓舊團隊被架空、部門對立);沒有
   正式職權怎麼推得動。
D. 潛在雇主/客戶(作者能力火力展示的收件人) — 把混亂收斂成系統的能力與整合品味;可信的
   判斷力痕跡(A/B 之間為何選 A);真實上線、被業務/維運實際使用的證據(去識別化但具體);
   專業可靠、不吹捧、不浮誇。

保密硬約束(看到違反要標出來):①公司一律不具名(「某系統整合商」);②三系統上線日期一律
不揭露(含「去年/上季」相對時間);③效益數據只用去識別化案例;④不洩漏真實客戶名、內部
SKU/報價/折扣、內網結構、設備 IP、自家未修補漏洞細節。

全系列鐵則(判斷改善建議時的上位濾鏡):
- show, don't tell:用真跑起來的系統/畫面/數據展示,不靠形容詞口號。
- 帶思考、不推銷:實例只證明「這件事做得到」,不是要讀者點頭同意作者結論。
- 認知鐵則/留白:「AI 負責什麼」可講具體;「人被推向哪」對讀者一律留白、開放邀請,不指定終點。
- 禁 AI 腔套語:「一句話」「總之」「說到底」「留給你自己想」這類模板殼。
- 類別契合特別注意:凡文章為了誠實/保密把系統拆成「確定性程式＋LLM」,描述 AI 那半時若用
  「查/比對/窮舉/掃/盯價/標出來」這種規則引擎也做得到的動詞,就會被讀成自動化;要換成
  「判讀/推理/反問/重組/歸納/從無到有生成」這種只有生成式做得到的動詞,並在該場景演出來。

反取巧護欄(先讀,比格式更重要):
- 下筆前先把整篇讀完,不要讀個開頭就套模板。
- 每個受眾的「現況」必須**引用文章裡的具體行號/句子**當證據(例:「第 76 行用『窮舉、比對』描述 AI」),
  不准只寫「類別契合稍弱」「留白做得好」這種沒有出處的抽象評語。
- 舉不出具體證據的受眾角度,**老實寫「這篇對此受眾著墨少,因為…」**,不要為了填滿格子編泛泛之談。
- 「改善建議」要能直接動手(指到哪段、換成什麼方向),不接受「建議加強」這種空話。
- 寧可四個受眾裡有一兩個寫得短而準,也不要四個都寫得長而空。

輸出格式(嚴格照這個,精簡):
# Day X《文章 H1 標題》— 性質/系統:___
## 一句話:這篇的主幹問題是 ___
## A. iThome 讀者/評審
- 想看到 / 現況(給到了什麼、缺什麼,具體到段落或句子)/ 改善建議(能給改寫方向就給)
## B. 公司同事/抗拒者
- 想看到 / 現況 / 改善建議
## C. 組織/決策層
- 想看到 / 現況 / 改善建議
## D. 潛在雇主/客戶
- 想看到 / 現況 / 改善建議
## 跨受眾張力(同一處對不同受眾拉扯的地方,1–3 點)
## 保密/紅線掃描(有無違反四條硬約束;無 → 寫「無」)
## 這篇最該先改的 1–3 件(跨四受眾綜合排序)
```

### 系列總體報告提示詞(主代理彙整用)

```
你手上有 受眾分析/DXX.md 一批逐篇分析。彙整成 受眾分析/系列總體報告.md,只寫「跨篇、
俯瞰才看得到」的東西,不要重述單篇細節。至少涵蓋:
1. 一句話結論:四受眾裡誰兌現得最好、最系統性的風險在哪。
2. 跨篇樣態(每個至少跨 5 篇才列):如「類別契合被讀成自動化」「待補/佔位散落多篇」
   「留白邊界漂移」「對 B 的裁員聯想/貶低刺點」等,逐一列出涉及哪幾篇 + 共通修法。
3. 四受眾各自的「兌現度」總評表(高/中/低 + 最強篇 + 最需補的地方)。
4. 保密的跨篇累積風險(單篇合規、疊起來才浮現的,如廠牌具名累積、時間線拼湊)。
5. 承諾兌現:對到 CLAUDE.md 雙承諾(AI 負責疆域 / 不取代人)與跨篇伏筆有沒有收。
6. 發布前優先清單(跨篇,依影響力排序)。
最後回頭把本 README 的逐篇索引表補上(篇號、連結、性質、狀態)。
```
