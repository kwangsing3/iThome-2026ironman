# 為什麼 AI 不可靠？我給你一個有趣的實際例子（WEBEX）——用提示逼 AI 做更深的研究

<!-- 前導 TL;DR（前 3–5 行）＝鉤子 + 結論先行。
     鉤子：我問 AI 一個 Webex API 問題，它給了一個「欄位名稱」——後來它自己承認：那是它編的。
     結論：AI 不可靠不是因為它笨，是它會「自信地填空」。破解法不是別用它，是用提示逼它「去查原始碼、別用猜的」。 -->

前面五天都在講「AI 會自信地錯」。今天不講,直接演給你看。

這是一段**真實對話**:我在做一個 Webex bot,想讓它顯示「已讀」頭像,就去問 AI 怎麼做。它給了我一個看起來很專業的 REST API 欄位——我照著找,**找不到**。追問之下,它自己承認:_「這個欄位名稱是我之前回答時編造的。」_

結論先給:**AI 不可靠,不是因為它笨,是因為它會「自信地填空」**。而破解法不是不用它,是用提示**逼它去讀原始碼、別用記憶猜**。這篇就拆這一整段。

## 我問了什麼？AI 一開始答得多漂亮？

<!-- 節首答案：問「Webex bot 怎麼標記已讀」，AI 立刻端出結構完整、格式工整的 REST API 用法。
     視覺錨點：chat_01（webhook JSON 結構）+ AI 端出 lastSeenActivityId 的那張截圖。 -->

情境很單純:我在做一個 Webex bot(webhook 模式),想讓它像人一樣顯示「已讀」——就是那個訊息下面的已讀頭像。我問 AI 該怎麼做。

它答得非常漂亮:條理分明、格式工整,甚至給了一個具體欄位 `lastSeenActivityId`,教我用 `PUT /memberships/{id}` 帶上這個欄位就能標記已讀。

<!-- 視覺錨點：貼 chat_01（webhook 結構那張，展示它連 JSON 結構都給得出來）+ 端出欄位的截圖。 -->

如果我是新手、或那天比較累,我大概就直接照做了——**它看起來太像查證過的了**。這正是 D5 說的那種危險:它錯的時候,語氣跟對的時候一模一樣篤定。

## 破綻在哪？我怎麼逼它露餡的？

<!-- 節首答案：照它給的欄位去找 → 官方 API 文件沒有這個欄位 → 我不接受它的解釋，改下提示「去讀原始碼」。
     視覺錨點：chat_15——AI 承認「這個欄位名稱是我之前回答時編造的，非常抱歉」。 -->

我照著 `lastSeenActivityId` 去翻 Webex 官方 REST API 文件——**沒有這個欄位**。

這時關鍵不是「罵它」,是**換一種提示**。我沒有問「你確定嗎?」(問這個它通常只會道歉然後再編一個),而是直接下指令:**「你研究一下 Webex JS SDK 的原理」「去看原始碼再給我答案」**——把它從「憑記憶回想」逼到「去讀真實來源」。

結果它自己抓出來了:

> **`lastSeenActivityId` 不存在於公開 REST API——這個欄位名稱是我之前回答時編造的,非常抱歉。**

這個畫面同時證明了兩件事:它**很強**(能瞬間組織出一大段專業回答),也**不可靠**(那段回答是錯的)。你要學的不是「信或不信」,而是**怎麼問、怎麼逼它、怎麼校正**——這才是這 30 天真正值錢的手感。

<!-- 視覺錨點（核心）：貼 chat_15，AI 承認編造的那段。這是全篇最有力的一張。 -->

這句話值得裱起來。它證明了 AI 的極限**不是能力問題,是機制問題**:當它「不知道」時,它不會空白,它會**生成一個最像答案的東西**——哪怕那東西不存在。

## 逼它去讀原始碼後，它給了什麼真答案？

<!-- 節首答案：一旦被導向真實來源（Webex JS SDK 原始碼），它更正為 updateLastSeen() → 內部
     conversation.acknowledge()，並明說這走內部 API、webhook 模式做不到。
     視覺錨點：結論表（PUT/公開REST/JS SDK/webhook 各自可用性）。 -->

同一個模型,換了提示、被指向真實來源(Webex JS SDK 原始碼)之後,答案品質完全不同:

- 真正的機制在 `updateLastSeen()`,它呼叫的是內部 API `conversation.acknowledge()`,**不是公開 REST endpoint**。
- 它還誠實補了一刀:我的 bot 用 webhook 模式,**根本做不到**這件事;要 JS SDK 的 websocket 模式才有可能。

<!-- 視覺錨點：貼結論表——四種做法 × 可用性（✅/❌），一眼看出「先前那個是錯的」。 -->

同一台機器,先給我一個編造的欄位,後給我一段有原始碼佐證的正解。**差別不在它變聰明了,在我換了問法**。這就是這篇最想給你的東西。

## 帶走什麼？把 AI 逼出深度的三個提示習慣

<!-- 節首答案：不是「別用 AI」，是三個把它從『回想』逼到『查證』的提示習慣。
     Tip 2：實作篇要明確給「帶走重點」，寫成可遷移的原則、非照抄。 -->

這段對話能遷移成三個隨手可用的習慣(不是這個案子專屬):

- **要來源,不要答案**:與其問「怎麼做」,不如問「**根據哪份文件/原始碼**,怎麼做」。逼它把答案掛在可查證的東西上,它就比較不敢編。
- **懷疑時,別問「你確定嗎」,改下「去讀 X」**:「你確定嗎」只會換來道歉 + 新的編造;「**去讀原始碼/官方文件再回答**」才會把它推向真實來源。
- **越具體越好查的細節,越要親自驗**:欄位名、API 路徑、參數這種「差一個字就錯」的東西,是幻覺重災區——AI 給了,你一定要自己對一次官方文件。

<!-- 一句適用邊界：這招適用「有客觀正解、可查證」的技術問題；主觀判斷題（該不該做）逼它查也沒用，那本來就該人決定。 -->

一句適用邊界:這三招對「有客觀正解、查得到」的技術問題最有效;至於「這件事該不該做」這種主觀判斷,逼它查原始碼也沒用——**那本來就不是它的活**。

## 那這代表 AI 沒用嗎？剛好相反

<!-- 節首答案：這代表 AI 要「放對位置」——它負責規模化的讀與生成，人負責校正與拍板。
     🧭 認知鐵則：不替讀者指定「你該當校正者」；把「怎麼用這份可靠」留給讀者。 -->

看完這段,很容易得出「AI 果然不能信」的結論——但那是看錯重點。

真正的重點是:**同一台機器,放錯位置(直接信)會害你,放對位置(逼它查、人來校正)會替你省下大把工。** 它能瞬間讀完 SDK 原始碼、能把散在各處的機制拼成一張表——這是人做起來很慢的事。它只是**不該站在沒人校正的終點**(這正是 D5 講的定位)。

至於認清這件事之後,你要把 AI 用得多深、把省下的力氣挪去哪——**那是你的選擇,這系列只負責把手感交到你手上**。

AI 會編造,但只要你用「去讀原始碼、別用猜的」逼它,它能自己把錯抓出來——**不可靠的破解法,是提示,不是放棄**。

但你也看到了:欄位名可以逼它查,「這件事該不該做」卻永遠得人拍板。那條把「該給 AI」和「該留給人」分開的線,到底怎麼劃?那是明天 D7 的核心命題。
