# 【AI 基礎應用 ①】從 0 開始：用 Azure AI Foundry 入門 AI 開發 + 第一個 tool call

前面聊完了怎麼在組織裡擺 AI、怎麼不打掉重練地平行導入。從今天起，接下來四天（D14–17）換成「做給你看」——把 AI 應用的骨架，一塊一塊拼給你看。

第一塊，就是把你從 0 帶到「跑出第一個會呼叫工具的 AI」。我不從理論開始，而是從**看得到的畫面**開始：先用 Azure AI Foundry 的介面跑出第一個回應，再把同一件事拿掉介面用 code 寫一次，最後讓它學會呼叫一個工具（tool call）。

這天結束，你手上不是一段筆記，是**一個真的會動手的 AI**——這也是接下來 D15（MCP）、D16（記憶）、D17（任務拆解）要一路長上去的底。

## 為什麼從 Azure AI Foundry 開始，而不是直接串 API？

<!-- 節首答案：因為平台把「模型部署、金鑰、遊樂場」都備好了，你能先用介面看懂 AI
     開發的形狀，再下沉到 code——降低第一次的門檻。 -->

因為對第一次做 AI 開發的人來說，**最貴的不是寫 code，是搞懂「一個 AI 應用到底由哪些東西組成」**。Azure AI Foundry 這類平台把模型部署、金鑰管理、可以直接對話的 Playground 都備好了，你能先用介面把「模型 → 輸入 → 輸出」這條路看清楚，再下沉到程式碼。

一句話：**先用介面建立直覺，再用 code 拿回控制權**。

> 註：D14–17 用 Azure AI Foundry 當教學載體，讓你從 0 體驗 AI 開發長什麼樣；它不是後面三系統的上線平台。手法（tool call、MCP、記憶、任務拆解）是共通的，換平台也成立。

## 介面怎麼跑出第一個 AI 回應？

第一步只有三個動作：在 Azure AI Foundry 建一個專案、部署一個聊天模型、打開 Playground 輸入一句話。

重點不在這句話它答得多好，而在你**親眼看到**：AI 應用最小的樣子，就是「輸入一段文字、拿回一段文字」。其他所有花俏功能，都是從這條最小路徑長出來的。

## 拿掉介面，同一件事用 code 長什麼樣？

<!-- 節首答案：把 Playground 做的事換成幾行 code——同一個 endpoint、同一個模型，
     只是改由你的程式送出請求。 -->

介面能跑，但真正的開發要能寫進你的系統裡。把上面那件事換成 code，其實很短：

```python
# 純代碼初探：把 Playground 做的事，改由程式送出
# （實際 endpoint / deployment 名稱以你的 Foundry 專案為準，此處為示意）
from openai import AzureOpenAI

client = AzureOpenAI(
    azure_endpoint="https://<your-foundry>.openai.azure.com/",  # 待補：去識別化
    api_key="<AZURE_OPENAI_API_KEY>",                            # 建議走環境變數
    api_version="2024-10-21",
)

resp = client.chat.completions.create(
    model="<your-deployment-name>",
    messages=[{"role": "user", "content": "用一句話解釋什麼是 tool call"}],
)
print(resp.choices[0].message.content)
```

差別只有一個：**送請求的人從「介面」換成「你的程式」**。模型、endpoint 都沒變。到這裡，你已經會用 code 跟 AI 對話了——但它現在只會「講」，還不會「做」。

## 怎麼讓 AI 不只會聊天，還會「呼叫一個工具」？

<!-- 節首答案：給它一個「工具定義」，讓模型自己決定要不要呼叫；它回一個 tool_call，
     你的程式執行後把結果餵回去，它再用結果回答。這一段是本篇的里程碑。
     視覺錨點：terminal 跑通的畫面（AI 決定呼叫工具 → 拿到結果 → 回答）。待補。 -->

讓 AI「動手」的關鍵字是 **tool call（工具呼叫，也叫 function calling）**：你把一個函式描述給模型，模型在需要時**自己決定**要呼叫它、並填好參數；你的程式執行、把結果餵回去，模型再根據結果回答。

注意這句話裡最重要的四個字——**「自己決定」**。工具是你寫的，但**要不要用、什麼時候用、參數填什麼，是模型的判斷**。這正是生成式 AI 和一段寫死的 if-else 的差別。

```python
# 給模型一個工具：查某個料號的庫存（示意工具，回假資料）
tools = [{
    "type": "function",
    "function": {
        "name": "get_stock",
        "description": "查詢指定料號目前的庫存數量",
        "parameters": {
            "type": "object",
            "properties": {"sku": {"type": "string", "description": "料號"}},
            "required": ["sku"],
        },
    },
}]

def get_stock(sku: str) -> int:
    return {"C9300-48P-A": 12, "C9120AXI-E": 0}.get(sku, 0)  # 示意資料

messages = [{"role": "user", "content": "C9300-48P-A 還有貨嗎？"}]
resp = client.chat.completions.create(
    model="<your-deployment-name>", messages=messages, tools=tools,
)

msg = resp.choices[0].message
if msg.tool_calls:                                   # ← 模型自己決定要呼叫工具
    import json
    call = msg.tool_calls[0]
    args = json.loads(call.function.arguments)
    result = get_stock(**args)                        # 你的程式執行
    messages += [msg, {                               # 把結果餵回去
        "role": "tool", "tool_call_id": call.id, "content": str(result),
    }]
    final = client.chat.completions.create(
        model="<your-deployment-name>", messages=messages, tools=tools,
    )
    print(final.choices[0].message.content)           # 模型用真實庫存回答
```

![tool call 跑通：AI 判斷要查庫存 → 呼叫工具 → 用回傳數字回答（截圖待補）](../docs/D14/tool_call_run.png)
_（待補：terminal 實際跑通的畫面。）_

跑通這一段，你就跨過了 AI 開發最重要的一道門檻：**AI 從「只會回答」變成「會呼叫你的系統」**。到這裡先停——「一個工具」就夠了；多個工具怎麼判斷、怎麼分派，是 D17 的事。

## 帶走什麼？

<!-- 依 Tip 2：實作篇明確給「可遷移的帶走重點」，每點對回主幹問題。 -->

- **AI 應用的最小形狀**：輸入文字 → 拿回文字。先用介面看懂，再用 code 拿回控制權。
- **介面與 code 是同一件事**：Playground 能做的，幾行 code 就能做；差別只在「誰送請求」。
- **tool call 的本質是「讓模型自己決定呼叫哪個函式、填什麼參數」**——這是生成式 AI 與寫死流程的分界。
- **一次先跑通一個工具**：把「判斷、參數、餵回結果」這個迴圈跑順，比一次塞很多工具更重要。
- **適用邊界**：tool call 適合「有明確函式、可執行、結果可餵回」的動作；主觀判斷題不靠工具解決。

     啟後鉤子（扣 D15 MCP）：但你剛剛那個工具，是手刻綁死在這支程式裡的。 -->

現在你有一個會呼叫工具的 AI 了。但你剛剛那個 `get_stock`，是**手刻、綁死在這支程式裡**的——換一個 AI、換一個專案，就得重寫一次。

有沒有一種**標準的方式**，把工具包成「任何 AI、任何應用都能接上來用」的介面？有，它叫 **MCP（Model Context Protocol）**。怎麼從 0 自己產一個 MCP 工具，是明天 D15 的事。
