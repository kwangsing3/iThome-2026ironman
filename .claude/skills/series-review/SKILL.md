# 系列整體評估基準(30 篇當一個整體看)

給 kwangsing3 的 2026 鐵人賽系列。系列主張:**「AI 負責人類到不了的地方,而不是取代人」**。

**分工**:`article-review` 管**單篇**該檢查什麼;本 skill 管**整體**——單篇各自都合格,但 30 篇拼起來是否成立、有沒有矛盾、有沒有俯瞰才看得到的風險。搭配 `CLAUDE.md`(排程、三部曲、主軸)與 `GLOSSARY.md` 一起看。

## 使用方式

1. 先過 **R1(反敘事的舉證負擔)**——這是本系列最大的整體風險,先看。
2. 再依 R2–R7 逐項俯瞰,**只回報有問題或有風險的項目**,不覆誦全部。
3. 每個發現給:**風險 → 為什麼(扣哪個主軸/紅線)→ 具體補法(改哪幾篇、加什麼證據)**。
4. 最後給「這一季最該先補的 3 件事」的優先序。
5. 涉及尚未寫的篇 → 標「待寫時盯這點」,不替作者杜撰內容。

## R1 反敘事的舉證負擔(最高風險,先看)

**本系列是反主流敘事**:全世界喊「AI 取代你」,作者喊「AI 不取代人」。反敘事天生**勾人**(好奇缺口),但**舉證責任極高**——讀者會用放大鏡等你證明,證據不足就崩成口號。

檢查全系列時盯:

- **最危險的崩塌點**:如果三系統(D18–26)裡**任何一個看起來真的讓某個職位消失了**,主張當場破功。三支後續引用篇(D20/23/26)務必 show 成「**人被釋放去做別的**」,不能讓讀者嗅到「其實是把人省掉了」。這是整季存亡級的一致性,俯瞰時必查。
- **承諾 B 是否只喊不證**:「不取代人」若全系列都在宣稱、沒有一篇拿真實案例證明「人被釋放後去了哪、做了什麼」,就是空承諾。承諾 B 沒有專屬篇,主要靠 D20/23/26 兌現——查這三篇有沒有真的兌現。
- **分眾各自的信任門檻不同**(俯瞰時一起看):
  - 🟢 新鮮人:主張是止痛藥,但會「半信半疑」——情緒接得住、信任要靠後面系統補,否則讀成雞湯。
  - 🟠 決策者:「不取代人」對想省人力的老闆是**逆風**(不取代人,ROI 在哪?)。留白原則在此有代價 → 決策者線(D10–14、D28)要用「**釋放出的人力去做了什麼有價值的事**」的案例補上,這是舉證不是指導棋。
  - 🔵 工程師:對主張近乎無感,全押在 D15–27 的真實技術;主張本身不加分,系統才是全部。
- **反 hype 一致性**:整季是否守住「未來感來自真的做到了」,沒有靠形容詞(顛覆/革命性/劃時代)撐主張(呼應 article-review §7)。

## R2 雙承諾的全系列兌現地圖

俯瞰承諾 A/B 在 30 篇裡的落點,查有沒有「喊了卻沒兌現」的段:

- **承諾 A(AI 負責疆域)**:D3 立論 → D4 落到本行規模牆 → D18–26 每系統第一篇證明「人做不到」→ 第三篇證明「AI 接手了」→ D27 收束。查這條鏈有沒有斷點。
- **承諾 B(不取代人)**:D7 劃分界線 → D20/23/26 主要證據 → D27/D29 保留人簽核 → D30 收束。**B 比 A 更容易空**,重點查。
- **「人往哪升級」的具體路徑**:CLAUDE.md 標為待補;俯瞰時確認是否仍是缺口,若補了要合乎「認知鐵則」(留白、非指導棋)。
- **敘事拍三「交棒」是否兌現(收尾三篇專查)**:D28(決策者版底座/AI 生產線)→ D29(組織版:舊團隊不被架空)→ D30(正式交棒:把底座交給讀者、價值由讀者定義)這條 through-line 有沒有立起來、前後接續而非各講各的。三個越界要抓:①把「發揮」寫成「抄我的 code」(違 §六.2 火力展示);②對 B 受眾寫成「我做好了你們得用」的強加;③藉底座敘事洩漏實際部署規模(違保密,見 R6)。

## R3 主張與用語的跨篇一致性

單篇看不出,30 篇並排才看得到的飄移:

- **核心主張措辭一致**:「AI 不取代人」這句在 D1/D7/D27/D30 等處是否**同一種講法**;尤其「人被推向哪」是否全系列都守**留白**、沒有某幾篇又寫死成「人該去做判斷/責任」(認知鐵則、article-review §3「不下指導棋」)。
- **GLOSSARY 用語一致**:三系統固定名、專有名詞中英對照全系列不飄移(向原廠下單系統別一下變報價系統)。
- **認知鐵則貫徹**:全系列是「協助認知」不是「改寫讀者想法」的語氣,沒有整篇變成說教。

## R4 讀者分眾:全程不棄養

D1 承諾了三條讀者線(新手/決策者/工程師),俯瞰確認**沒有哪條線在中途被放生**:

- 每條線在 D1 標的天數是否真的服務到該對象(如工程師線 D15–27 夠硬、新手線 D1–7 沒術語轟炸)。
- **中段續航風險**:D1–14 概念偏多,是否靠 D6/D13 的 code 示範與真實案例錨點撐住,避免工程師與一般讀者在實作段前流失(呼應 article-review §0 硬門檻是主要防線)。
- **決策者 ROI 缺口**(接 R1):決策者最想要的「投資回報」是否在某處被具體舉證,而非只有留白。

## R5 敘事弧線、節奏與回收

- **五階段完整**:認知 → 思考 → 設計 → 實現 → 收尾,比重與 CLAUDE.md 相符,階段轉場有銜接(承先啟後,呼應 article-framework Tip 3)。
- **三部曲節奏一致**:三系統都走「人類極限 → 實作 → 後續引用」,第一篇用疆界框架不抱怨(article-review §3)。
- **常駐角色回收**:D8 那位「把自動化當威脅」的同事,是否在 D20/23/26 回來變成使用者——前後呼應,兌現「不取代人」。
- **學習契約對帳**:D1 開場列的承諾/地圖,D30 是否逐條回收。這是頭尾閉環,俯瞰必查。**另確認 D30 有回收 D01 埋的「交棒伏筆」**(D01 承諾 B 那條已預告「D30 把底座交到你手上、換你發揮」)——這張跨篇支票 D30 必須核銷,否則拍三跳票。

## R6 保密的「跨篇累積」風險(單篇 review 抓不到,本 skill 專責)

單篇各自去識別化都合格,但**多篇拼起來可能反推**——這是俯瞰層級才看得到的紅線(呼應 article-review §5、GLOSSARY §四):

- **公司身分反推**:數篇的產業細節、技術棧(Cisco/CCW)、設備規模、客戶類型拼起來,是否足以指認「某系統整合商」是誰?任何會縮小範圍的修飾語(如「筆者所處的」)跨篇累積都要警覺。
- **上線時間反推**:雖然每篇都不揭露日期,但「發文時間 + 相對描述」跨篇拼湊是否洩漏時序?連「去年/上季」也要全系列掃。
- **攻擊面累積**:CVE 篇(D21–23)與設備篇(D24–26)合起來,是否洩漏自家設備清單/版本弱點/內網結構到可被利用?單篇安全不代表合起來安全。

## R7 類別契合(生成式 AI)的全系列可見度

報名組別是**生成式 AI**。俯瞰查「LLM/生成式實際做了什麼判斷或生成」是否**在整季持續可見**,而不是只有標題掛 AI、內容讀成自動化專案(呼應 CLAUDE.md §六.1):

- 三系統每篇是否都講清楚 LLM 在其中的**具體角色**(生成什麼、判斷什麼),而非純 pipeline/爬蟲/SQL。
- 生成式 AI 的出場是否**分散在全系列**,不是擠在一兩篇。
